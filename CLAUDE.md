## 1. Что мы строим

CRM-система для частной медицинской клиники (3 кабинета). Это **не замена YCLIENTS**, а надстройка над ним:

1. **Омниканальный инбокс** — переписка с пациентами из Instagram Direct и WhatsApp в одном окне.
2. **AI-агент** — ведёт диалог с пациентом, отвечает на типовые вопросы, проверяет свободные слоты и записывает на приём. Сложные вопросы эскалирует людям.
3. **Push-уведомления** сотрудникам при эскалации.
4. **Дашборд метрик** — воронка обращений, приёмы, выручка, загрузка кабинетов.

Веб-интерфейс: аккуратный, спокойный, без визуального шума. Целевой пользователь — администратор клиники, который сидит в системе весь день. Приоритет: плотность информации и скорость, а не декоративность.

## 2. Главный архитектурный принцип

> **YCLIENTS — источник истины по расписанию, записям и выручке.**

Мы не ведём собственное расписание и не считаем деньги сами. Мы читаем данные из YCLIENTS, кэшируем их у себя для аналитики и пишем обратно записи, созданные агентом.

Причина: администраторы продолжат работать в YCLIENTS. Любая попытка держать своё расписание как второй источник истины приведёт к рассинхрону и двойным записям в один слот.

**Следствия, которые нельзя нарушать:**
- Перед `create_booking` слот **всегда** перепроверяется запросом в YCLIENTS в реальном времени. Кэш слотов — только для показа, не для решения.
- Изменения из YCLIENTS прилетают вебхуками и обновляют локальную копию.
- Локальные таблицы `Appointment`, `Patient`, `Staff` — это **проекция** YCLIENTS, а не мастер-данные. У каждой есть `yclients*Id`.

## 3. Стек и инфраструктура

- **Next.js (App Router) + TypeScript** — веб-интерфейс и REST-эндпоинты
- **PostgreSQL + Prisma** — основная БД
- **Tailwind CSS** — стили. shadcn/ui для базовых компонентов.
- **Redis + BullMQ** — очереди для обработки вебхуков, ретраев, отложенных задач (напоминания о визите)
- **WebSocket-сервер (отдельный Node-процесс)** — live-обновление инбокса. Next.js на serverless долго держать сокет не умеет, поэтому realtime вынесен в отдельный сервис.
- **Web Push (VAPID + Service Worker)** — push-уведомления сотрудникам
- **Docker Compose** — деплой

**Хостинг: только российский** (Selectel / Timeweb / Yandex Cloud). Vercel и зарубежные БД исключены — см. раздел 7. Это архитектурное ограничение, не предпочтение.

### Структура репозитория

```
apps/
  web/          Next.js — UI + API routes
  realtime/     WebSocket-сервер
  worker/       BullMQ-воркеры (вебхуки, синк, напоминания)
packages/
  db/           Prisma-схема и клиент
  integrations/ адаптеры: yclients/, instagram/, whatsapp/
  agent/        LLM-агент: промпты, tools, оркестрация
  shared/       типы, zod-схемы, утилиты
```

## 4. Модель данных

Базовый набор сущностей. Расширяй, но не ломай ключевые связи.

```prisma
model Patient {
  id           String   @id @default(cuid())
  yclientsId   Int?     @unique
  phone        String   @unique      // нормализованный E.164 — единственный надёжный ключ матчинга
  name         String?
  firstSeenAt  DateTime
  sourceId     String?               // источник первого обращения
}

model Conversation {
  id            String   @id @default(cuid())
  patientId     String?
  channel       Channel               // INSTAGRAM | WHATSAPP | TELEGRAM
  externalUserId String                // ig scoped id / номер в wa
  status        ConvStatus            // BOT_ACTIVE | ESCALATED | HUMAN_TAKEOVER | CLOSED
  assignedToId  String?
  startedAt     DateTime
  lastMessageAt DateTime
  @@unique([channel, externalUserId])
}

model Message {
  id             String   @id @default(cuid())
  conversationId String
  direction      Direction   // IN | OUT
  authorType     AuthorType  // PATIENT | BOT | STAFF
  authorId       String?
  body           String
  attachments    Json?
  externalId     String?  @unique   // идемпотентность вебхуков
  createdAt      DateTime
}

model Appointment {
  id               String   @id @default(cuid())
  yclientsRecordId Int      @unique
  patientId        String
  staffId          String
  roomId           String?
  serviceIds       Int[]
  startAt          DateTime
  durationMin      Int
  status           ApptStatus  // CREATED | CONFIRMED | ARRIVED | NO_SHOW | CANCELLED
  isFirstVisit     Boolean
  revenue          Decimal  @db.Decimal(12,2)  @default(0)
  sourceId         String?
  conversationId   String?     // атрибуция: запись пришла из диалога с агентом
}

model Staff        { id, yclientsStaffId, name, specialty, isActive }
model Room         { id, yclientsResourceId, name, workingHours Json }
model Source       { id, code, title }   // instagram | whatsapp | site | call | offline | referral
model Escalation   { id, conversationId, reason, createdAt, resolvedById?, resolvedAt? }
model StaffUser    { id, name, role, pushSubscriptions Json[] }
model SyncCursor   { entity, lastSyncedAt, lastCursor }  // для инкрементальной синхронизации
```

**Правила:**
- Телефон нормализуется в E.164 **на входе**, всегда. Матчинг пациентов только по нему.
- Все внешние ID (`externalId`, `yclientsRecordId`) — уникальные индексы. Вебхуки приходят повторно, идемпотентность обязательна.
- Мягкое удаление вместо `DELETE` для всего, что касается пациентов и записей.

## 5. Интеграции

### YCLIENTS
- REST API + вебхуки. Партнёрский токен + user token, ключи филиала — в env.
- **Начальная выгрузка обязательна**: перед запуском импортируем всю историю клиентов и визитов. Без неё метрики «новые пациенты» и «первичный/повторный» будут врать в первый месяц.
- Rate limit: все вызовы через единый клиент с очередью и экспоненциальным ретраем. Никаких прямых `fetch` из бизнес-логики.
- Кабинеты в YCLIENTS ведутся как **ресурсы**. Если у клиники они не заведены — маппинг «специалист → кабинет» лежит в конфиге; уточнить у заказчика до реализации метрики загрузки.

### Instagram
Meta Graph API (Instagram Messaging), вебхук на `messages`. Требует Business-аккаунт, привязанный к Facebook-странице, и review приложения. **24-часовое окно** на ответ вне messaging tags — учитывай в логике агента.

### WhatsApp
Через провайдера (Wazzup24 / Green API), а не напрямую с Meta Cloud API. Провайдер держит сессию и даёт один вебхук. Адаптер пишем так, чтобы смена провайдера была заменой одного файла.

### Единый интерфейс адаптера
Каждый канал реализует один и тот же контракт:

```ts
interface ChannelAdapter {
  parseWebhook(raw: unknown): IncomingMessage[]
  sendText(externalUserId: string, text: string): Promise<{ externalId: string }>
  sendAttachment(...): Promise<...>
}
```

Бизнес-логика не знает, из какого канала пришло сообщение.

### Внутренние чаты сотрудников

Внутренний чат клиники — отдельная подсистема, не `Conversation/Message`.
Причина: `Conversation/Message` — пациентские внешние каналы, они участвуют в
воронке обращений, 24-часовых окнах, эскалациях и правилах агента. Служебная
переписка сотрудников туда не попадает.

Модели: `InternalChatRoom`, `InternalChatParticipant`,
`InternalChatMessage`. Есть общий чат клиники (`GENERAL`, `directKey=general`)
и личные диалоги (`DIRECT`, `directKey` — отсортированная пара `StaffUser.id`).
Личные чаты опираются только на реальных `StaffUser` из аутентификации.
Удаление сообщений мягкое (`deletedAt`), голосовые сообщения пока хранятся как
короткое audio dataUrl во вложениях JSON; при появлении object storage формат
вложения сохраняется, меняется только источник файла.

## 6. AI-агент

### Инструменты (function calling)

| Tool | Назначение |
|---|---|
| `get_services()` | услуги, цены, длительность |
| `get_free_slots(serviceId, staffId?, dateFrom, dateTo)` | свободные окна из YCLIENTS |
| `create_booking(patientPhone, name, serviceId, staffId, startAt)` | создать запись |
| `reschedule_booking(recordId, newStartAt)` | перенести |
| `cancel_booking(recordId)` | отменить |
| `get_patient_appointments(patientId)` | история визитов (только для идентифицированного пациента) |
| `escalate(reason, urgency)` | позвать человека |

### Жёсткие правила поведения агента

1. **Никакой медицины.** Агент не обсуждает симптомы, диагнозы, назначения, дозировки, противопоказания, результаты анализов. Любой такой вопрос → немедленный `escalate`. Это не рекомендация, это требование.
2. **Не выдумывает.** Цены, услуги, адрес, время работы — только из tool-вызовов. Если данных нет — эскалация, а не догадка.
3. **Слот перепроверяется перед записью.** Всегда.
4. **Перехват человеком.** Как только сотрудник отправил сообщение вручную, диалог переходит в `HUMAN_TAKEOVER` и агент молчит минимум 12 часов или до явного возврата кнопкой. Бот, перебивающий администратора, — худший баг в этой системе.
5. **Персональные данные не уходят в LLM.** В промпт передаём `patientId`, имя (для обращения) и контекст визитов. ФИО целиком, диагнозы, любые медданные — нет.

### Триггеры эскалации
`escalate` от агента · пациент просит человека · ключевые слова (жалоба, боль, вернуть деньги, юрист, врач ошибся) · три неудачных попытки понять запрос · любой медицинский вопрос · молчание агента > 3 мин при активном диалоге.

### Порядок внедрения агента
Реализуем **сначала suggest-режим**: агент генерирует черновик, администратор жмёт «отправить». Автономная отправка включается позже фича-флагом `AGENT_AUTONOMOUS=false` по умолчанию. Не реализуй автономный режим, пока suggest не отработан на живых диалогах.

## 7. Персональные данные и право

Проект работает с медицинскими данными в РФ. Это влияет на код:

- **152-ФЗ**: хранение и обработка ПДн — на серверах в РФ. Никаких зарубежных БД, логгеров, аналитик, CDN с персданными.
- **Врачебная тайна (ст. 13 323-ФЗ)**: медданные не покидают периметр. В сторонний LLM API они не уходят (см. правило 5 выше).
- **Согласие на обработку ПДн**: при первом контакте в мессенджере агент отправляет ссылку на политику и фиксирует факт согласия в БД.
- **Логи**: тела сообщений не попадают в общие логи и в внешние error-трекеры. Только идентификаторы.
- **Доступ**: ролевая модель + аудит-лог на просмотр карточки пациента.
- Секреты — только в env, никогда в репозитории. `.env.example` держим актуальным.

## 8. Метрики — точные определения

Считаются из локальной проекции данных. Эти определения согласованы с заказчиком, менять их можно только с его подтверждением.

| Метрика | Определение |
|---|---|
| **Обращения** | Диалог считается новым обращением, если предыдущее сообщение пациента было ≥ 24 ч назад. Разрез: по источнику. |
| **Новые пациенты** | Первое появление номера телефона в базе (с учётом импортированной истории YCLIENTS). |
| **Записавшиеся** | Appointment со статусом ≠ CANCELLED, созданный в периоде. |
| **Пришедшие** | Appointment со статусом `ARRIVED`. Зависит от того, что администраторы проставляют статус посещения в YCLIENTS. |
| **Первичные** | Первый в истории визит пациента со статусом `ARRIVED`. |
| **Повторные** | Все последующие визиты со статусом `ARRIVED`. |
| **Выручка** | Сумма по оплаченным визитам из YCLIENTS. Собственного финучёта не ведём. Разрез: по специалистам. |
| **Загрузка кабинета** | `занятые минуты / (рабочие минуты кабинета за период)`. По каждому из 3 кабинетов отдельно. |

**Реализация:** дневные агрегаты в `DailyRollup`, пересчёт воркером ночью + инкрементально при изменениях. Дашборд читает роллапы, не сырые таблицы.

## 9. Дизайн интерфейса

- Плотная информационная сетка, спокойная палитра, один акцентный цвет. Не «лендинг», а рабочий инструмент.
- Инбокс — трёхколоночный: список диалогов / переписка / карточка пациента с историей визитов.
- Эскалации визуально выделены и не теряются.
- Дашборд: карточки ключевых цифр сверху, графики и разрезы ниже. Период переключается одним контролом.
- Всё критичное доступно с клавиатуры. Администратор работает быстро.
- **Полная мобильная адаптация** (решение заказчика, июль 2026 — заменяет прежнее «мобильно только инбокс»). Внедряется поэтапно: (1) инбокс, карточка пациента, форма звонка; (2) настройки; (3) дашборд/аналитика. Дашборд перестаёт быть десктоп-only.

## 10. Этапы

Работаем строго по порядку. Не начинай следующий этап, пока предыдущий не принят.

1. **Фундамент** — Prisma-схема, интеграция с YCLIENTS, начальная выгрузка истории, вебхуки, синхронизация. Дашборд со всеми метриками.
2. **Инбокс** — Instagram + WhatsApp, карточка пациента, ручные ответы, web push, realtime.
3. **Агент в suggest-режиме** — tools, промпт, черновики ответов, эскалации.
4. **Автономный агент** — узкий сценарий (запись / перенос / цены / адрес / часы работы), всё остальное в эскалацию.

## 11. Как работать со мной

- **Перед реализацией новой подсистемы — короткий план в чат, потом код.** Не пиши сразу 15 файлов.
- Маленькие связные коммиты, осмысленные сообщения на русском или английском — но единообразно.
- TypeScript strict. `any` — только с комментарием, объясняющим почему.
- Валидация всех внешних входов (вебхуки, формы, query) через zod.
- Тесты обязательны для: нормализации телефонов, парсинга вебхуков, расчёта метрик, логики выбора слотов. Остальное — по ситуации.
- Если требование неоднозначно (особенно в метриках и в поведении агента) — **спроси, не угадывай**. Цена неверной догадки здесь выше цены вопроса.
- Не добавляй зависимости без необходимости. Не рефактори то, о чём не просили.
- Если предлагаешь отойти от архитектуры в этом файле — сначала объясни почему, потом делай.
