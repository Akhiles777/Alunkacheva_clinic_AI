## 1. Что мы строим

CRM-система для частной медицинской клиники (3 кабинета). Это **не замена YCLIENTS**, а надстройка над ним:

1. **Омниканальный инбокс** — переписка с пациентами из Instagram Direct и WhatsApp в одном окне.
2. **AI-агент** — ведёт диалог с пациентом, отвечает на типовые вопросы, проверяет свободные слоты и записывает на приём. Сложные вопросы эскалирует людям.
3. **Push-уведомления** сотрудникам при эскалации.
4. **Дашборд метрик** — воронка обращений, приёмы, выручка, загрузка кабинетов.

Веб-интерфейс: аккуратный, спокойный, без визуального шума. Целевой пользователь — администратор клиники, который сидит в системе весь день. Приоритет: плотность информации и скорость, а не декоративность.

## 2. Главный архитектурный принцип

> **YCLIENTS — источник истины по расписанию, записям и выручке.**

Мы не ведём собственное расписание и не считаем деньги сами. Мы читаем данные из YCLIENTS, кэшируем их у себя для аналитики и пишем обратно записи, созданные агентом.

Причина: администраторы продолжат работать в YCLIENTS. Любая попытка держать своё расписание как второй источник истины приведёт к рассинхрону и двойным записям в один слот.

**Следствия, которые нельзя нарушать:**
- Перед `create_booking` слот **всегда** перепроверяется запросом в YCLIENTS в реальном времени. Кэш слотов — только для показа, не для решения.
- Изменения из YCLIENTS прилетают вебхуками и обновляют локальную копию.
- Локальные таблицы `Appointment`, `Patient`, `Staff` — это **проекция** YCLIENTS, а не мастер-данные. У каждой есть `yclients*Id`.

## 3. Стек и инфраструктура

Раздел описывает то, что есть в коде. Прежняя редакция описывала замысел —
монорепозиторий с очередями и отдельным realtime-сервисом, — которого никогда
не существовало. Расхождение документации с реальностью само по себе дефект:
по нему планируют работу, и планы оказываются про чужую систему.

- **Next.js 16 (App Router) + TypeScript strict** — UI, серверные действия и
  REST-эндпоинты в одном приложении
- **PostgreSQL + Prisma 7** — основная БД, миграции в `prisma/migrations`
- **Tailwind CSS + `tokens.css`** — стили; правила и палитра в `DESIGN.md`
- **Расписание внутри процесса** (`lib/server/scheduler.ts`), запускается из
  `instrumentation.ts` при старте. Полный круг выгрузки — 15 мин, короткий — 3
  мин; тем же кругом идут возврат диалогов агенту и добор неотвеченных.
- **Web Push (VAPID + Service Worker)** — уведомления сотрудникам
- **pm2 + nginx** на российском VDS; выкат — `deploy/pm2-deploy.sh`, порядок и
  откат — в `DEPLOY.md`

**Чего в проекте НЕТ, вопреки прежнему тексту раздела:**

- **Redis и BullMQ.** Очередей нет. Отложенные задачи и ретраи делает тот же
  внутренний планировщик; если понадобится настоящая очередь — это отдельное
  решение, а не «как задумано».
- **Отдельного WebSocket-сервера.** Инбокс обновляется опросом раз в 6 секунд.
  Работает и переживает перезапуск приложения; сокет вводить только под
  измеренную нужду.
- **Монорепозитория.** Один пакет, одна `package.json`.
- **Docker Compose как боевого способа запуска.** Файл есть и годится для
  локального стенда, прод живёт под pm2.

**Хостинг: только российский** (Selectel / Timeweb / Yandex Cloud). Vercel и
зарубежные БД исключены — см. раздел 7. Это архитектурное ограничение, не
предпочтение. Демо-стенд на Vercel допустим только с вымышленными данными.

## 4. Модель данных

Базовый набор сущностей. Расширяй, но не ломай ключевые связи.

```prisma
model Patient {
  id           String   @id @default(cuid())
  yclientsId   Int?     @unique
  phone        String   @unique      // нормализованный E.164 — единственный надёжный ключ матчинга
  name         String?
  firstSeenAt  DateTime
  sourceId     String?               // источник первого обращения
}

model Conversation {
  id            String   @id @default(cuid())
  patientId     String?
  channel       Channel               // INSTAGRAM | WHATSAPP | TELEGRAM
  externalUserId String                // ig scoped id / номер в wa
  status        ConvStatus            // BOT_ACTIVE | ESCALATED | HUMAN_TAKEOVER | CLOSED
  assignedToId  String?
  startedAt     DateTime
  lastMessageAt DateTime
  @@unique([channel, externalUserId])
}

model Message {
  id             String   @id @default(cuid())
  conversationId String
  direction      Direction   // IN | OUT
  authorType     AuthorType  // PATIENT | BOT | STAFF
  authorId       String?
  body           String
  attachments    Json?
  externalId     String?  @unique   // идемпотентность вебхуков
  createdAt      DateTime
}

model Appointment {
  id               String   @id @default(cuid())
  yclientsRecordId Int      @unique
  patientId        String
  staffId          String
  roomId           String?
  serviceIds       Int[]
  startAt          DateTime
  durationMin      Int
  status           ApptStatus  // CREATED | CONFIRMED | ARRIVED | NO_SHOW | CANCELLED
  isFirstVisit     Boolean
  revenue          Decimal  @db.Decimal(12,2)  @default(0)
  sourceId         String?
  conversationId   String?     // атрибуция: запись пришла из диалога с агентом
}

model Staff        { id, yclientsStaffId, name, specialty, isActive }
model Room         { id, yclientsResourceId, name, workingHours Json }
model Source       { id, code, title }   // instagram | whatsapp | site | call | offline | referral
model Escalation   { id, conversationId, reason, createdAt, resolvedById?, resolvedAt? }
model StaffUser    { id, name, role, pushSubscriptions Json[] }
model SyncCursor   { entity, lastSyncedAt, lastCursor }  // для инкрементальной синхронизации
```

**Правила:**
- Телефон нормализуется в E.164 **на входе**, всегда. Матчинг пациентов только по нему.
- Все внешние ID (`externalId`, `yclientsRecordId`) — уникальные индексы. Вебхуки приходят повторно, идемпотентность обязательна.
- Мягкое удаление вместо `DELETE` для всего, что касается пациентов и записей.

## 5. Интеграции

### YCLIENTS
- REST API + вебхуки. Партнёрский токен + user token, ключи филиала — в env.
- **Начальная выгрузка обязательна**: перед запуском импортируем всю историю клиентов и визитов. Без неё метрики «новые пациенты» и «первичный/повторный» будут врать в первый месяц.
- Rate limit: все вызовы через единый клиент с очередью и экспоненциальным ретраем. Никаких прямых `fetch` из бизнес-логики.
- Кабинеты в YCLIENTS ведутся как **ресурсы**. Если у клиники они не заведены — маппинг «специалист → кабинет» лежит в конфиге; уточнить у заказчика до реализации метрики загрузки.

### Instagram
Meta Graph API (Instagram Messaging), вебхук на `messages`. Требует Business-аккаунт, привязанный к Facebook-странице, и review приложения. **24-часовое окно** на ответ вне messaging tags — учитывай в логике агента.

### WhatsApp
Через провайдера (Wazzup24 / Green API), а не напрямую с Meta Cloud API. Провайдер держит сессию и даёт один вебхук. Адаптер пишем так, чтобы смена провайдера была заменой одного файла.

### Написать пациенту первым

Одна дорога на все экраны: инбокс, курсы, «Кому позвонить». Переписка с
пациентом уже есть — пишем в неё; нет и канал WhatsApp — отправляем по номеру
из карточки и заводим диалог с НАСТОЯЩИМ адресом чата, чтобы ответ пациента
попал в ту же переписку; нет и канал Instagram — отказ словами: первым там
пишет пациент, и делать вид, что это не так, нельзя.

**Сообщение, которое не ушло, не показывается как отправленное.** Прежде
кнопка «Написать» только писала в базу: заводила диалог с адресом `local-…`,
экран говорил «Сообщение отправлено», а в WhatsApp не уходило ничего. Это хуже
ошибки — система уверенно врала о выполненной работе, и администратор больше
не возвращался к этому пациенту. Найти такие диалоги на боевых данных —
`scripts/local-dialogs.ts`.

### Единый интерфейс адаптера
Каждый канал реализует один и тот же контракт:

```ts
interface ChannelAdapter {
  parseWebhook(raw: unknown): IncomingMessage[]
  sendText(externalUserId: string, text: string): Promise<{ externalId: string }>
  sendAttachment(...): Promise<...>
}
```

Бизнес-логика не знает, из какого канала пришло сообщение.

### Отправка: причина отказа записывается всегда

Клиент Telegram возвращал `null` на любую неудачу, и причина исчезала: в базе
оставалось «FAILED» без объяснения. На боевом сервере это выглядело как «бот
молчит без причины» — а он отвечал, просто ответы не уходили, и разбираться
было не с чем. Теперь причина ложится в `Message.failureReason` («Telegram
403: bot was blocked», «TimeoutError», «Too Many Requests»): это три разные
проблемы и три разных действия.

**Входящие и исходящие ломаются порознь.** Вебхук работает, когда Telegram
стучится К НАМ; ответы уходят, когда МЫ стучимся к api.telegram.org. С
российского сервера второе работает с перебоями, и картина «update-ы доходят,
ответы не уходят» — штатная. Поэтому у отправки одна повторная попытка через
полсекунды (больше нельзя: вебхук обязан ответить Telegram быстро, иначе он
пришлёт update заново и пациент получит два ответа). Разбор цепочки —
`scripts/telegram-check.ts`.

### Внутренние чаты сотрудников

Внутренний чат клиники — отдельная подсистема, не `Conversation/Message`.
Причина: `Conversation/Message` — пациентские внешние каналы, они участвуют в
воронке обращений, 24-часовых окнах, эскалациях и правилах агента. Служебная
переписка сотрудников туда не попадает.

Модели: `InternalChatRoom`, `InternalChatParticipant`,
`InternalChatMessage`. Есть общий чат клиники (`GENERAL`, `directKey=general`)
и личные диалоги (`DIRECT`, `directKey` — отсортированная пара `StaffUser.id`).
Личные чаты опираются только на реальных `StaffUser` из аутентификации.
Удаление сообщений мягкое (`deletedAt`), голосовые сообщения пока хранятся как
короткое audio dataUrl во вложениях JSON; при появлении object storage формат
вложения сохраняется, меняется только источник файла.

## 6. AI-агент

### Инструменты (function calling)

| Tool | Назначение |
|---|---|
| `get_services()` | услуги, цены, длительность — пациенту только то, что он может купить (`lib/agent/price-list.ts`): заготовки с ценой 0 и 1 ₽ и служебные позиции «для персонала» в ответ не идут, «0 мин» не печатается, длинный список обрезается с предложением спросить конкретную услугу |
| `get_free_slots(serviceId, staffId?, dateFrom, dateTo)` | свободные окна из YCLIENTS |
| `create_booking(patientPhone, name, serviceId, staffId, startAt)` | создать запись |
| `reschedule_booking(recordId, newStartAt)` | перенести |
| `cancel_booking(recordId)` | отменить |
| `get_patient_appointments(patientId)` | история визитов (только для идентифицированного пациента) |
| `escalate(reason, urgency)` | позвать человека |

### Разделение зон (решение заказчика, август 2026 — заменяет прежнее «никакой медицины»)

| Отвечает агент | Только человек |
|---|---|
| адрес, график работы | свободные окна |
| условия приёма врачей и специалистов | запись, переносы, отмены |
| информация об услугах и ценах | жалобы и претензии |
| согласие на обработку ПДн | уточнения по конкретному пациенту |
| условия при отмене записи | вопросы без готовой справки |
| подготовка к процедурам, противопоказания | |

**Расписанием агент не распоряжается.** Записи он не создаёт: окна, переносы и
отмены ведёт администратор. Это осознанный выбор заказчика — продажу закрывает
человек.

### Жёсткие правила поведения агента

1. **Медицинские темы — только дословной справкой клиники.** Подготовка и
   противопоказания разрешены агенту, но отвечать он может исключительно тем
   текстом, который клиника завела в справочнике и утвердила сама. Подходящей
   записи нет → `escalate`. Собственной медицинской эрудицией модель не
   пользуется никогда: сочинённое противопоказание — это вред пациенту и риск
   по ст. 13 323-ФЗ.
2. **Не выдумывает.** Цены, услуги, адрес, время работы — только из tool-вызовов. Если данных нет — эскалация, а не догадка.
3. **Слот перепроверяется перед записью.** Всегда.
4. **Перехват человеком.** Как только сотрудник отправил сообщение вручную, диалог переходит в `HUMAN_TAKEOVER` и агент молчит **4 часа** (`HANDBACK_HOURS`) от последнего сообщения переписки или до явного возврата кнопкой. Бот, перебивающий администратора, — худший баг в этой системе.

   Через четыре часа тишины диалог возвращается агенту сам (решение заказчика,
   август 2026 — прежде были сутки, до них «минимум 12 часов» без
   автоматического возврата). Сутки означали, что вечернее обращение ждало
   агента до следующего вечера, а добор неотвеченных до него уже не дотягивался:
   он догоняет сообщения не старше 6 часов (`MAX_AGE_HOURS`), и возврат через
   24 часа был возвратом на бумаге. Пауза агента и срок возврата — **одно
   число** (`HUMAN_TAKEOVER_HOURS = HANDBACK_HOURS`): иначе агент уже отвечает,
   а диалог всё ещё числится за человеком.

   **Второй раз за день агент не здоровается.** Разговор шёл утром, через
   четыре часа человек спрашивает адрес — и слышит «Здравствуйте!» от
   собеседника, который час назад отвечал ему на другой вопрос: это выдаёт
   автоответчик и читается как потеря памяти. Приветствие снимается с начала
   ответа, если сегодня мы уже здоровались в этом диалоге (`greetedToday` +
   `stripLeadingGreeting`). Главное правило вежливости при этом сильнее:
   **поздоровался человек — здороваемся и мы**, сколько бы раз за день это ни
   повторилось. «Здравствуйте, напомните адрес» получает «Здравствуйте! Наш
   адрес…». Приветствие снимается только тогда, когда человек не здоровался
   сам (`shouldDropGreeting`).

   **Возврат не значит «переиграть старую переписку».** Агент отвечает только
   на сообщения, пришедшие ПОСЛЕ возврата: границей служит `botPausedUntil`,
   который при автоматическом возврате не снимается, а остаётся в прошлом.
   Иначе через четыре часа приходило «Хорошо, если появятся вопросы — я здесь»
   в ответ на реплику, на которую администратор уже ответил. Кнопка «Вернуть
   агенту» паузу снимает совсем — там человек передаёт разговор осознанно,
   вместе с последним вопросом.

   Возврат снимает и открытую эскалацию: иначе статус говорит «ведёт агент», а
   добор неотвеченных диалог обходит. Согласие и история при этом не
   сбрасываются — агент помнит переписку и знает записи пациента.

   Пока диалог ведёт человек и пациент ждёт ответа дольше 30 минут,
   администраторам уходит напоминание — **один раз** на ожидание. Повторы об
   одном и том же перестают читать, а вместе с ними перестают читать и новые.
5. **Персональные данные не уходят в LLM.** В промпт передаём `patientId`, имя (для обращения) и контекст визитов. ФИО целиком, диагнозы, любые медданные — нет.

### Наблюдаемость агента

Каждая попытка ответить — строка `AgentRun`: исход (`OK` / `TIMEOUT` /
`PROVIDER_ERROR` / `EMPTY_RESPONSE` / `ESCALATED` / `SUPPRESSED`), задержка,
модель, токены, ссылка на предыдущую попытку у повтора. ПДн там нет: только
идентификаторы и техническая причина, очищенная от эха запроса (§7).

`SUPPRESSED` — намеренное молчание (пауза после перехвата, сообщение старше
возврата). В надёжность не входит: агент не пытался и не мог ответить.
`ESCALATED` — тоже не отказ: часть тем ему запрещена.

**«Закрыл сам» — не «ответил».** Разговор считается закрытым агентом, только
если сутки после его ответа не вмешался сотрудник, не завелась эскалация и
пациент не переспросил в ближайшие два часа. Агент, ответивший невпопад и
вызвавший три уточнения, в наивной метрике выглядел бы успешным.

**Две меры пользы, и они отвечают на разные вопросы.**

«Сэкономленное время администратора» — сколько работы агент сделал за людей.
Требует базы по темам: сравнивать вопрос про адрес с разбором жалобы нельзя,
поэтому тема без пяти ручных ответов в расчёт не идёт вовсе.

«Сколько пациенты не ждали» (`waitingSaved`) — сколько ожидания снято с людей.
Считается из двух ИЗМЕРЕННЫХ медиан без единой придуманной величины: столько
отвечает агент и столько ждали бы человека **в рабочие часы**. Ночное ожидание
в сравнение не берётся намеренно: агент работает круглосуточно, человек нет, и
это завысило бы пользу в разы. Оценка снизу, и так она подписана. Отрицательной
не бывает: на маленькой выборке агент бывает медленнее, и минус там — шум.

**Сэкономленное время не показывается в одиночку.** Рядом всегда встречное
число: сколько разговоров ушло людям и сколько времени они на них потратили.
Основа сравнения — медиана РУЧНЫХ ответов по той же теме за 90 дней, обрезанная
получасом сверху (дольше — это ожидание, а не написание). Тема, по которой
ручных ответов меньше пяти, в расчёт не идёт вовсе: её называют числом
«недостаточно данных», а не заполняют средним по больнице.

Везде медиана, не среднее: одно ночное сообщение с ответом через двенадцать
часов сдвигает среднее так, что типичный случай исчезает. Среднее стоит рядом
вторым числом.

### Пробелы в справочнике

Эскалации «не понял вопрос» и «медицинский вопрос без готового ответа» — это
вопросы, на которые у клиники нет заведённого ответа. Экран «Настройки →
Ассистент → Пробелы» собирает их за 90 дней, группирует похожие простой
нормализацией и пересечением слов (той же, которой агент ищет ответ:
`stemsOf`) и показывает рядом то, чем ответил администратор в переписке.
Векторной базы здесь нет намеренно: вопросов десятки, а не миллионы, и группу
всё равно читает человек.

**Запись справочника не создаётся автоматически ни при каком условии.** Кнопка
«Создать запись из этого ответа» добавляет ЧЕРНОВИК в редактор ниже; в базе он
появляется только после того, как человек прочитал текст и нажал «Сохранить».
Причина: администратор писал конкретному пациенту, зная его случай («вам с
вашим сроком лучше не надо»), а справка отвечает всем. Проверяется структурно
— тестом, что в `lib/agent/gaps.ts` и `lib/server/knowledge-gaps.ts` нет ни
одной записи в справочник.

**Медицинскую справку утверждает врач.** Группа считается медицинской, если
эскалация была `MEDICAL_QUESTION` или в вопросе есть медицинское слово; список
слов намеренно широкий — лишнее согласование стоит минуты, пропущенное
противопоказание стоит здоровья. Такая запись создаётся выключенной, помечена
`needsDoctorApproval` и **не может быть включена**, пока её не утвердил
пользователь с ролью DOCTOR или OWNER; агент неутверждённую запись не видит
(`usableKnowledgeWhere`). Правка текста утверждение снимает и выключает запись:
утверждение относится к тому тексту, который врач прочитал.

**Польза записи считается по журналу попыток** (`AgentRun.knowledgeEntryIds`),
а не отдельным счётчиком в `KnowledgeEntry`: счётчик разъедется с фактами при
первом же сбое пересчёта. Рядом с числом стоит дата начала журнала — иначе ноль
читается как «запись бесполезна», хотя означает «журнала тогда не было».

### Инструкция клиники и живая проверка

Текст из «Настройки → Ассистент» доходит до модели (`intakePrompt(settings.prompt)`).
Связь была разорвана: поле сохранялось и никуда не шло, агент вёл разговор по
образцу, что бы клиника ни написала. Инструкция заменяет ПОРЯДОК разговора о
записи и только его; базовые ограничения идут перед ней и отсюда не
отключаются. Длина обрезана (`MAX_INSTRUCTION_CHARS`): чем длиннее регламент,
тем слабее модель держится за «не обещай запись».

**Все указания — одним системным сообщением.** Их было четыре подряд, и модель
отвечала на последнее из них: ответ начинался с «Acknowledged. Я — справочная
служба…» и пересказа собственных правил, а настоящий ответ обрывался на
полуслове. Найдено живым прогоном, не рассуждением.

**Пересказ инструкций пациенту не уходит.** Модель приписывает к ответу абзац
о самой себе — «Acknowledged. Я — справочная служба клиники, отвечаю на „вы“,
опираюсь только на справку…», иногда по-английски и с рассуждением о роли.
Просьбами это не лечится: на «не подтверждай получение правил» модель отвечает
«Принято». Поэтому у ответа есть якорь: пациенту уходит только то, что стоит
после строки «ОТВЕТ:», всё до неё отрезается, что бы там ни оказалось
(`stripPreamble`). Лимит ответа поднят до 700 токенов: четырёхсот не хватало,
и настоящий ответ обрывался на полуслове — «Работаем с 09:00 до 21:00. Вос».

**`\b` в правилах агента не используется.** В JavaScript граница слова
опирается на латинский `\w` и рядом с кириллицей не находится вовсе:
`/принято\b/` не совпадает со строкой «Принято.» никогда. Правило выглядит
рабочим и молча не срабатывает. Границы задаёт `lib/agent/word-boundary.ts`
(`wordRe`, `phraseRe`) — через отсутствие соседней буквы.

**Оборванный ответ пациенту не уходит.** Модель тратит часть лимита на
преамбулу перед меткой — мы её отрезаем, но заплачено за неё уже из бюджета,
и настоящий ответ упирается в потолок. Пациент получил «…и доступности запис»
и не мог понять, дописал бот или пропала связь. При `finish_reason: length`
ответ обрезается по последнему законченному предложению: лучше короче, но
целиком.

**Подмена собеседника запрещена отдельным правилом.** На вопрос «Разият
Ризвановна принимает взрослых?» модель ответила «да, Ирина принимает
взрослых» — назвала другого человека и подтвердила то, о чём не спрашивали.
Пациент запомнит имя и придёт не к тому врачу. Специалиста или услуги нет в
справке — так и говорим и передаём администратору; отвечать «да» или «нет» про
врача, которого в справке нет, нельзя ни при каких условиях.

**Ответ вне роли пациенту не уходит** (`offCharacter`). На вопросе о
беременности модель сорвалась в собственную защитную формулировку: «I'm Claude,
an AI assistant made by Anthropic…» — по делу, но по-английски и от чужого
имени. Такой ответ считается несостоявшимся: агент молчит и зовёт человека —
ровно то, что и требуется на медицинском вопросе. Полагаться здесь на просьбы
в промпте нельзя: модель срывается непредсказуемо.

Проверка на живой модели — `scripts/agent-live-test.ts` (по умолчанию только
показывает сценарии, спрашивает по `--run`, стоит денег; `--only=2,6` — переспросить
названные). Шесть сценариев: запись, присланные данные, свободное время,
медицинский вопрос, цена, противопоказание без справки.

### Триггеры эскалации
`escalate` от агента · пациент просит человека · ключевые слова (жалоба, боль, вернуть деньги, юрист, врач ошибся) · три неудачных попытки понять запрос · любой медицинский вопрос · молчание агента > 3 мин при активном диалоге.

### Порядок внедрения агента
Агент работает автономно в своей зоне (справочные вопросы) — записи он не
создаёт, поэтому цена ошибки ограничена текстом ответа. Для пациентских
каналов с записью по-прежнему реализуем **сначала suggest-режим**: агент генерирует черновик, администратор жмёт «отправить». Автономная отправка включается позже фича-флагом `AGENT_AUTONOMOUS=false` по умолчанию. Не реализуй автономный режим, пока suggest не отработан на живых диалогах.

### Личное дело пациента

В карточке — раздел «Личное дело» (`lib/metrics/patient-profile.ts`): что
человек берёт, как часто ходит, сколько принёс, как общается и что учесть в
разговоре. Считается на нашем сервере из своих данных.

**Переписка не уходит во внешнюю модель.** «Разбор диалога» здесь означает
счёт по своим правилам — время суток, длина сообщений, скорость ответа,
приветствие, «вы»/«ты», просьбы позвать человека, — а не пересказ LLM.
Переписка с клиникой содержит жалобы на здоровье: это врачебная тайна
(ст. 13 323-ФЗ) и персональные данные (§7), и отправить её наружу ради
портрета нельзя, сколько бы пользы это ни обещало. Отправка текстов
переписки в LLM возможна только по отдельному решению заказчика, с
обезличиванием и согласием, покрывающим такую обработку.

**Совет без основания не показывается.** У каждого вывода свой порог
наблюдений (`MIN_MESSAGES_FOR_STYLE`, `MIN_VISITS_FOR_RHYTHM`); не набралось —
пишем это словами. Причина простая: администратор понесёт наш вывод в
разговор с живым человеком, и придуманный «портрет» там дороже отсутствия
портрета. Рядом с каждым советом стоит его основание — «приветствие в 82%
сообщений», а не «вежливый».

Дело собирается на лету при открытии карточки, а не хранится снимком:
хранимый портрет устаревает молча, и никто не знает, когда он был верен.

## 7. Персональные данные и право

Проект работает с медицинскими данными в РФ. Это влияет на код:

- **152-ФЗ**: хранение и обработка ПДн — на серверах в РФ. Никаких зарубежных БД, логгеров, аналитик, CDN с персданными.
- **Врачебная тайна (ст. 13 323-ФЗ)**: медданные не покидают периметр. В сторонний LLM API они не уходят (см. правило 5 выше).
- **Согласие на обработку ПДн**: при первом контакте в мессенджере агент отправляет ссылку на политику и фиксирует факт согласия в БД.
- **Логи**: тела сообщений не попадают в общие логи и в внешние error-трекеры. Только идентификаторы.
- **Доступ**: ролевая модель + аудит-лог на просмотр карточки пациента.
- Секреты — только в env, никогда в репозитории. `.env.example` держим актуальным.

## 8. Метрики — точные определения

Считаются из локальной проекции данных. Эти определения согласованы с заказчиком, менять их можно только с его подтверждением.

| Метрика | Определение |
|---|---|
| **Обращения** | Сообщение пациента считается новым обращением, если предыдущее его сообщение было ≥ 24 ч назад. Считается по сообщениям, а не по числу заведённых диалогов: постоянный пациент пишет в тот же чат месяцами. Разрез: по источнику. |
| **Новые пациенты** | Первое появление номера телефона в базе (с учётом импортированной истории YCLIENTS). Карточки, у которых дату первого обращения взять было неоткуда (перенос из YCLIENTS без визитов), помечены `firstSeenExact = false` и не считаются новыми ни в одном месяце: иначе вся база разом становится притоком месяца выгрузки. |
| **Записавшиеся** | Appointment со статусом ≠ CANCELLED, созданный в периоде (по `createdAtYclients`). В отчёте показывается рядом с числом приёмов, приходящихся на период: это разные вопросы, и подменять одно другим нельзя. |
| **Пришедшие** | Appointment со статусом `ARRIVED`. Зависит от того, что администраторы проставляют статус посещения в YCLIENTS. |
| **Разобранность визитов** | Прошедший приём (сутки после начала, `MARK_GRACE_HOURS`) со статусом `CREATED`/`CONFIRMED` — **неразобранный**: он не состоялся и не неявка, мы просто не знаем. Считается рядом с неявками ВСЕГДА: «Неявки 0%» означает либо «неявок нет», либо «никто ничего не отмечает», и различить их можно только этим числом. Деньги неразобранных считаются отдельно — в выручку они не входят и не видны ни в одном разрезе. Сверка на боевых данных — `scripts/attendance-check.ts`. |
| **Первичные** | Первый в истории визит пациента со статусом `ARRIVED`. |
| **Повторные** | Все последующие визиты со статусом `ARRIVED`. |
| **Выручка** | Деньги, принятые в этот день: стоимость услуг из записи YCLIENTS плюс курсы, проданные в этот день. Ноль в записи остаётся нулём — подставлять цену из прайса нельзя. Так выглядит сеанс курса: деньги за него клиника получила при продаже (БОС-терапия, 28 000 ₽ за 10 сеансов), и подстановка считала бы их заново на каждом сеансе — за день выходило 61 280 ₽ вместо 43 480 ₽. Сама продажа курса пробивается кассовой операцией, а не записью приёма, и её сумма — выручка дня покупки (решение заказчика, август 2026). Двойного счёта нет: сеансы дают ноль, а продажа, проведённая записью, в кассовые покупки не попадает. **Скидка 100% на курсовой услуге — это оплата курсом, а не подарок**
(`courseAwareSource`). Сеанс закрывают на абонемент двумя способами: списанием
(цена обнуляется сама) и скидкой 100%. Второй считался подарком, и сеанс не
занимал места в курсе: курс из десяти показывал «7/10, выпал из графика» у
пациентки, сходившей восемь раз, а сам сеанс стоял подписью «бесплатно» под
услугой за 2 800 ₽. Денег правило не меняет — ноль в обоих случаях, — меняет
только зачёт сеанса в курс. Курсовую услугу даром не отдают.

Ноль без скидки и без курсовой услуги означает, что цену забыли проставить: считаем за ноль и показываем администратору в «Настройки → Интеграции» строкой «без суммы в записи». Словом «бесплатно» ноль не подписывается ни на одном экране: это вывод, а не факт. На экранах стоит то, что записано, — «скидка 100%» или «сумма не указана». КОНТРОЛЬ и БОС-терапия приносят деньги в отчётах, и «бесплатно» напротив них читается как ошибка платформы. Собственного финучёта не ведём. Разрез: по специалистам. |
| **Средний чек** | Деньги периода ÷ **оплаченные чеки**: приёмы с ненулевой суммой плюс курсы, проданные в этом периоде (у продажи есть клиент и сумма — это чек). Сеанс оплаченного курса и бесплатный приём не идут ни в числитель, ни в знаменатель: деля на всех пришедших, экран показывал 300 ₽ в день, где из десяти приёмов восемь были курсовыми сеансами по нулю, — такое число падает ровно тогда, когда клиника продаёт больше курсов (решение заказчика, август 2026). |
| **Загрузка кабинета** | `занятые минуты / (рабочие минуты кабинета за период)`. Рабочие минуты — из графика клиники («Настройки → Клиника»), не константой: зашитые 9:00–21:00 при восьмичасовом дне занижали загрузку в полтора раза. По каждому из 3 кабинетов отдельно. |

**Услуга без приёмов — четыре разных случая.** Строка «Без приёмов за период»
перечисляла подряд всё, у чего ноль: дубли справочника, служебные позиции,
заготовки без цены и настоящие незаказанные услуги. «Остеопатия, приём Ирины»
стояла в списке «без приёмов», хотя приёмы по ней идут каждый день — записаны
они на другую строку с тем же названием. Разные причины требуют разных
действий, поэтому показаны врозь (`classifyIdleServices`); сравнение названий
не различает регистр, «ё» и кавычки — именно так справочник и задваивается.

Приёмы держатся за конкретную СТРОКУ справочника, а не за название. Отсюда
правило: разрез по услугам считается по строкам, а дубль надо слить, а не
прятать. Найти дубли на боевых данных — `scripts/attendance-check.ts`.

**Цена услуги: чья она.** Справочник приезжает из YCLIENTS, и выгрузка
переписывала цену каждый круг — правка в «Настройки → Услуги» не держалась и
четверти часа, что читалось как «не сохраняется». Изменённая руками цена
помечается `priceLocked` и выгрузкой не трогается; что говорит YCLIENTS,
хранится рядом (`yclientsPrice`) и показано на экране кнопкой возврата. На
выручку это не влияет никак: цена из справочника в стоимость визита не
подставляется (§8), она нужна ассистенту для ответа пациенту и для плановой
цены курса.

**Курсы.** Курсовые услуги отмечаются в «Настройки → Услуги»
(`Service.isCourse`), размер курса и его цена живут там же; подсказать состав
может `scripts/courses-detect.ts`. Если рядом с услугой заведена карточка курса
(«БОС-терапия, курс», 28 000 ₽, сеансов 10), цена и размер берутся из неё —
клиника уже ответила на этот вопрос, и вариантов может быть несколько (курс из
4 и курс из 10).

Продажа курса — **кассовая операция**, а не запись приёма: у неё есть клиент,
сумма и номер продажи, но нет услуги. Хранится отдельно от курса
(`CoursePurchase`), потому что это разные вещи: продажа — деньги конкретного
дня, курс — программа сеансов, которая появляется, когда пациент начал ходить.
Пока продажа жила внутри курса, её деньги ждали первого сеанса и в выручку дня
покупки не попадали. Изредка курс проводят оплатой в самой записи — тогда его
деньги уже посчитаны выручкой того визита, и второй раз их не добавляют:
различает эти два случая `Course.origin`. Отбираем строки с клиентом, с видом
проданного и без привязки к записи; строки одной продажи складываем по
`sold_item_id`, возвраты вычитаем. Покупкой курса считается то, что покрывает
хотя бы половину его цены, — иначе цена одного сеанса открывала бы курс.

Услугу продаже назначает сумма: 28 000 ₽ — это курс БОС, а не курс НАК по
1 000 ₽ за сеанс. Если по сумме подходят двое или ни одного при двух
кандидатах, продажа остаётся неразобранной, курс не создаётся, и число таких
продаж выгрузка называет вслух. Догадок в цепочке нет.

Деньги за курс принадлежат тому, кто его ведёт. Специалиста называют сеансы
курса; если сеансов ещё нет — визиты этого пациента по этой услуге, а если и
их нет — единственный специалист услуги в клинике. Когда услугу ведут двое и
истории нет, продажа остаётся без специалиста: в выручке и в разрезе по
услугам её деньги есть, а в разрезе по людям они показываются отдельной
строкой «курсы без специалиста». Сумма строк, не сходящаяся с итогом, — это
дефект; приписанный наугад человек — ложь про конкретного сотрудника.

**Сеанс, покрытый оплаченным курсом, денег дня не даёт — независимо от того,
что стоит в записи.** Обычно YCLIENTS сам обнуляет стоимость при закрытии
приёма на курс, но администратор иногда закрывает его по прайсу, и в записи
остаётся цена сеанса. Это те же рубли, что клиника получила при продаже:
пациентка купила 30 сеансов, сходила ровно 30 раз, и два приёма стояли сверху
по 2 800 ₽. Решает не цена, а наличие оплаченного свободного места в курсе:
есть — сеанс курса, цена снимается (`revenueSource = PREPAID`) и в записи, и в
составе визита; нет — за приём действительно заплатили, и сумма остаётся.
Снимается ровно курсовая часть: приём бывает из двух позиций, и «сеанс БОС +
капельница» не должен терять стоимость капельницы (`revenueAfterCourse`). Это
правило распределения, а не спор с YCLIENTS (§2): сумма продажи остаётся
выручкой дня покупки и второй раз не считается. Курс, проведённый оплатой в
самой записи (`origin = MANUAL`), не трогаем — там деньги как раз в визите.
Сколько сеансов пришлось обнулить, выгрузка называет числом
(`courseSessionsRepriced`).

Приём курсовой услуги, которому места в курсе не нашлось, — настоящая оплата
(сеанс сверх курса или разовый визит). На экранах он подписан «отдельно»,
разобрать конкретный случай — `scripts/patient-courses.ts`. Цена ещё не
состоявшегося приёма деньгами не считается вовсе: это план из прайса, который
обнулится при закрытии.

`Course` пересобирается после каждой выгрузки (`linkCourses`) и объясняет нули:
«сеанс 4 из 10», а не безымянный «0 ₽». Место в курсе занимает и предстоящий
сеанс — иначе следующая покупка открывала бы курс раньше времени; отмена и
неявка курс не тратят.

**Занятое место и пройденный сеанс — разные числа.** `sessionsUsed` — только
СОСТОЯВШИЕСЯ приёмы, `sessionsBooked` — записанные впереди. Пока предстоящие
сеансы считались пройденными, курс из десяти показывал «10/10, курс пройден» у
пациентки, сходившей четыре раза и записанной на оставшиеся шесть:
администратор видит закрытый курс и дальше человека не зовёт. На экранах это
«4/10 · записан ещё на 6».

### Экономика курсов

Четыре метрики в `lib/metrics/courses.ts`, одни и те же в отчётах (вкладка
«Курсы»), в кабинете владельца и у ИИ-аналитика:

| Метрика | Определение |
|---|---|
| **Доходимость** (`courseCompletion`) | Среди курсов, купленных в периоде: дошли до конца ÷ **решившиеся** (дошедшие плюс брошенные). Брошен — сеансы остались, будущей записи нет, с последнего сеанса прошло больше порога. Идущий курс в долю НЕ входит: курс, купленный вчера, не «недошедший», и считая его таким, каждый свежий месяц показывал бы ноль. Порога нет — курс не решён, и это отдельное число, а не «идёт». |
| **Обязательства** (`outstandingCourseValue`) | Оплаченные и не проведённые сеансы в рублях, на сегодня. **Это не выручка** — деньги получены в дни продаж и посчитаны тогда же (§8); подпись «обязательства и потенциал, а не выручка» стоит рядом с числом всегда, иначе его складывают с деньгами месяца. Отдельно — сумма у выпавших из графика: те же деньги, но человека сначала надо позвать. |
| **Ритм сеансов** (`sessionInterval`) | Медиана дней между соседними состоявшимися сеансами; среднее рядом вторым числом. Один отпуск в три недели сдвигает среднее так, что типичный ритм исчезает. По одному сеансу интервала не бывает — тогда «—», а не ноль. |
| **Повторные покупки** (`courseRepurchase`) | Среди курсов, законченных в периоде: купил ли пациент ещё один курс в течение `REPURCHASE_WINDOW_DAYS` (90). Закончившие недавно в долю не идут — у них не было времени вернуться; их число показано отдельно как «ждём». |

Пороги «выпал» берутся оттуда же, откуда их берёт очередь «Кому позвонить»:
услуга, затем запасной порог клиники. Одна и та же дата не может быть
«брошенным курсом» на одном экране и «идущим» на другом.

**Реализация:** дневные агрегаты в `DailyRollup`, пересчёт воркером ночью + инкрементально при изменениях. Дашборд читает роллапы, не сырые таблицы.

**ИИ-аналитик не складывает числа сам.** Владелец спросил про неделю 17–23
августа, аналитик сложил дневные суммы и назвал 300 100 ₽ там, где в отчёте
396 080 ₽: пропустил день и ошибся в сложении оставшихся. Число выглядело
посчитанным и было неверным — это хуже отказа отвечать. Поэтому недельные и
месячные итоги приходят в сводку ГОТОВЫМИ, из тех же функций, что рисуют
график (`getWeeklyDynamics`), а промпт прямо запрещает складывать дни. Дневные
строки нужны, чтобы объяснить ПОЧЕМУ, но итог всегда берётся готовым.

**Ноль пишется числом.** Поле, опускавшееся при нуле, читалось как «такого
среза нет»: аналитик отвечал, что разбивки по новым пациентам по дням не
существует, хотя в тот день их просто не было. Пропущенное число неотличимо от
отсутствующего — та же ошибка, что структурный ноль на экране. Первичные,
повторные, новые, неявки и отмены стоят в каждой дневной строке всегда, и оба
числа названы явно: вычитать повторных из приёмов аналитик не должен, вычитание
— тоже арифметика.

Первой строкой сводки стоит сегодняшняя дата. Аналитик отвечал «в данных за
сегодня (25 августа)», когда шло пятое сентября: какая из дат сегодняшняя, он
выводил сам и ошибался.

Там же — график клиники и её нерабочие дни. Без них аналитик выводил график из
пустых дней: «22-го и 23-го клиника вообще не принимала», хотя суббота у
клиники рабочая. Пустой день в рабочую дату означает, что никто не пришёл, и
это другой вывод.

**Одна функция на метрику.** Отчёты, ИИ-аналитик владельца и разборы в
`scripts/` считают одними и теми же функциями (`getDashboardMetricsDb`,
`countInquiriesFromDb`). Своя арифметика на экране — источник двух правд:
владелец поверит удобной, а расхождение обнаружится в разговоре с клиентом.

**Имя визита — это его состав** (`lib/visit-title.ts`, одна функция на всю
систему). У записи бывает несколько услуг: мать записывает себя и ребёнка
одной записью, к приёму добавляют капельницу. Пока именем визита была ПЕРВАЯ
услуга, а сумма показывалась за все, «Взрослый приём — остеопатия, 13 000 ₽»
противоречило прайсу (приём стоит 8 000) и читалось как ошибка платформы.
Одна услуга — её название; несколько — все через «+», повторы схлопываются.
Состав расписывается ценами отдельной строкой только когда услуг больше одной:
одну перечислять незачем, она уже названа. Так называют визит карточка
пациента, экран дня, разбор выручки, расписание и экран врача — иначе на одном
экране «Взрослый», на другом «Взрослый + Детский», и это две правды об одной
записи.

**Состав визита исчезает вместе с услугой.** Услугу из записи убирают, и
строки состава обязаны уйти: итог дня считается по сумме визита, а разрез по
услугам — по составу, и расхождение означает две разные суммы на двух экранах.
Чистка идёт на каждой выгрузке независимо от того, менялась ли запись: сама она
с тех пор не менялась, и в разбор больше никогда не попадёт (у записи
1871049840 в YCLIENTS услуги нет, сумма ноль, а в составе висели 5 000 ₽).

**Запись, исчезнувшая из YCLIENTS, помечается удалённой, а не отменённой.**
Отменённый визит YCLIENTS показывает сам (со своим статусом) — он остаётся в
карточке пациента, о нём договорились. Запись, которой в YCLIENTS больше нет,
там удалили: чаще всего это перенос, сделанный пересозданием. Пока такие
записи становились «отменёнными», на один слот в карточке стояло три строки —
«отменён», «отменён» и «запланирован», — и понять, придёт человек или нет,
было нельзя. Строка из базы не исчезает (`deletedAt`), и если YCLIENTS покажет
запись снова, выгрузка снимет отметку.

**Откуда пришёл пациент.** Источник обращения в YCLIENTS не заполняет никто:
на боевых данных он не проставлен ни у одного визита из 741, и разрез воронки
по источникам показывал одну строку. Поэтому источник выводится из переписки
(`lib/metrics/source-attribution.ts`): если у того же пациента есть диалог, где
он писал в окне «14 дней до создания записи — час после», источник записи — это
канал того диалога. Диалогов несколько — берётся тот, где сообщение ближе к
созданию записи. Переписки рядом нет — источник остаётся **неизвестным**.

Три состояния различает `Appointment.sourceConfidence`: `MANUAL` — проставил
человек, `DERIVED` — выведено из переписки, `UNKNOWN` — не знаем. На экранах
они подписаны по-разному: «Instagram» и «Instagram · из переписки» — разные
утверждения, и администратор должен видеть, правит он догадку системы или
чужой ответ.

**Ручной источник не переписывается никогда** — ни выгрузкой, ни пересчётом.
Администратор, проставивший его, говорил с человеком; пересчёт, затирающий
такую отметку, обесценивает саму возможность её поставить, и второй раз её
никто вводить не станет.

**Неизвестное не подменяется звонком.** Отсутствие переписки не доказывает
звонок: человек мог прийти по рекомендации, с улицы, из старой записи. Строка
«Источник неизвестен» стоит в разрезе наравне с остальными и со своим числом —
без неё доли считались бы от одних опознанных записей, и «WhatsApp — 100%»
означало бы одну запись из семисот сорока одной.

Пересчёт идемпотентен и идёт полным кругом выгрузки (`recomputeAppointmentSources`),
а по свежим пациентам — коротким. Разовый разбор истории — `scripts/backfill-sources.ts`
(по умолчанию сухой прогон, запись по `--apply`).

**Свежесть данных.** Статусы визитов приходят только выгрузкой. Вебхуков от
YCLIENTS не будет: в настройках филиала места для нашего адреса нет (проверено
с владельцем, август 2026; за всё время — ноль событий). Поэтому выгрузка
двухскоростная, расписание живёт внутри процесса (`lib/server/scheduler.ts`):

- **полный круг** каждые `SYNC_INTERVAL_MIN` (15 мин) — справочники, клиенты,
  записи за месяц назад и три месяца вперёд, один месяц истории по кругу,
  касса за 200 дней, пересборка курсов;
- **короткий круг** каждые `SYNC_FAST_INTERVAL_MIN` (3 мин) — только записи за
  два дня назад и месяц вперёд, два-три запроса. Курсор он не двигает,
  справочники, кассу и курсы не трогает и **ничего не отменяет**: сверка «наше,
  чего YCLIENTS не показал, отменено» верна только для широкого окна, иначе
  запись, перенесённая с завтра на октябрь, объявляется удалённой. Отмены —
  работа полного круга. Тем же кругом идут возврат диалогов агенту и добор
  неотвеченных.

Последний месяц полный круг перечитывает всегда: отметку «пришёл»
администратор ставит задним числом. Ручной запуск — `/api/cron/sync`
(`?fast=1` — короткий круг, `?check=1` — состояние без выгрузки). Проверка
цепочки — `scripts/yclients-health.ts`.

### Кому позвонить

Рабочая очередь администратора (`/queue`, `lib/metrics/callback-queue.ts`):
выпал из курса · курс на финише · не пришёл · давно не был. Четыре повода, у
каждой строки на экране написано ЕЁ основание — список без основания читается
как «система так решила», и по нему перестают звонить.

**Пороги — из настроек, а не из констант.** Сначала порог услуги
(`Service.stalledAfterDays`), затем запасной порог клиники («Настройки →
Клиника»). Нет ни того, ни другого — человек в очередь не идёт, и число таких
случаев экран называет вслух: это незаполненная настройка, а не отсутствие
кандидатов. Через сколько дней пациент считается потерянным, решает клиника.
Экран курсов считает «выпал» тем же правилом — иначе на одном экране «выпал»,
на другом человека нет, и обе строки одинаково не заслуживают доверия.

**Из списка убирает только настоящая будущая запись.** Отправленное сообщение
не убирает: «написали» — это ещё не «придёт», и очередь, которая чистится от
добрых намерений, перестаёт быть очередью.

**Состояние 24-часового окна видно ДО попытки отправки.** В закрытое окно
свободный текст не уйдёт, и узнавать об этом из повисшего сообщения нельзя.

**Деньги двух разных сортов и подписаны по-разному.** У курса они уже получены
— это обязательство отработать; у остальных поводов это цена по прайсу, то
есть план, а не выручка (§8). Складывать их в одно число нельзя, поэтому в
строке написано, какие они. Цена неизвестна — так и написано, ноль вместо неё
не ставится.

**Что дал список, считается по отметкам обращений** (`CallbackOutreach`):
запись человека, которому никто не звонил, — не заслуга очереди. Иначе раздел
приписывал бы себе весь поток клиники и всегда выглядел бы успешным. Деньги в
результате — только состоявшихся визитов.

## 9. Дизайн интерфейса

- Плотная информационная сетка, спокойная палитра, один акцентный цвет. Не «лендинг», а рабочий инструмент.
- Инбокс — трёхколоночный: список диалогов / переписка / карточка пациента с историей визитов.
- Эскалации визуально выделены и не теряются.
- Дашборд: карточки ключевых цифр сверху, графики и разрезы ниже. Период переключается одним контролом.
- Всё критичное доступно с клавиатуры. Администратор работает быстро.
- **Полная мобильная адаптация** (решение заказчика, июль 2026 — заменяет прежнее «мобильно только инбокс»). Внедряется поэтапно: (1) инбокс, карточка пациента, форма звонка; (2) настройки; (3) дашборд/аналитика. Дашборд перестаёт быть десктоп-only.

## 10. Этапы

Работаем строго по порядку. Не начинай следующий этап, пока предыдущий не принят.

1. **Фундамент** — Prisma-схема, интеграция с YCLIENTS, начальная выгрузка истории, вебхуки, синхронизация. Дашборд со всеми метриками.
2. **Инбокс** — Instagram + WhatsApp, карточка пациента, ручные ответы, web push, realtime.
3. **Агент в suggest-режиме** — tools, промпт, черновики ответов, эскалации.
4. **Автономный агент** — узкий сценарий (запись / перенос / цены / адрес / часы работы), всё остальное в эскалацию.
