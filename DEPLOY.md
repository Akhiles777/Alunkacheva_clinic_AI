# Публикация

## Важное ограничение

CLAUDE.md §7: платформа работает с медицинскими персональными данными, а 152-ФЗ
требует хранить и обрабатывать их на серверах в РФ. **Vercel и зарубежные базы
для боевой эксплуатации не подходят.**

Поэтому разделяем два контура:

| Контур | Где | Данные |
|---|---|---|
| Демо для согласования с заказчиком | Vercel | **только вымышленные**, засеянные `prisma db seed` |
| Боевой | российский хостинг (Selectel / Timeweb / Yandex Cloud) | реальные |

На демо-стенде не должно быть ни одного настоящего пациента, номера телефона
или переписки.

---

## Vercel (демо)

### 1. База

Нужна доступная извне PostgreSQL. Для демо годится любая управляемая база;
строку подключения кладём в `DATABASE_URL`.

### 2. Переменные окружения

В проекте Vercel → Settings → Environment Variables:

| Переменная | Значение | Обязательна |
|---|---|---|
| `DATABASE_URL` | строка подключения к PostgreSQL | да |
| `SESSION_SECRET` | `openssl rand -base64 32` | да — без неё не работает вход |
| `CREDENTIAL_MASTER_KEY` | `openssl rand -base64 32` | для раздела «Интеграции» |
| `ALLOW_SELF_REGISTRATION` | `false` | нет (по умолчанию закрыта) |
| `DATABASE_POOL_MAX` | `5` | нет |
| `ROUTER_AI` | ключ ИИ-ассистента | нет — без него работает локальный движок |
| `VAPID_PUBLIC` / `VAPID_PRIVATE` / `NEXT_PUBLIC_VAPID_PUBLIC` | `npx web-push generate-vapid-keys` | нет — без них push не отправляется |

`SESSION_SECRET` — ключ подписи сессионной куки. Сборка и запуск без него
проходят, но попытка войти отказывает с явной ошибкой в логах. Так задумано:
работать с известным секретом нельзя — куку подделает кто угодно и войдёт
владельцем.

Переменные окружения нужны **в рантайме, а не на сборке**: сборка намеренно не
требует ни базы, ни секретов, иначе недоступная БД валит деплой.

### 3. Миграции и начальные данные

Сборка намеренно **не** ходит в базу — иначе недоступная БД валит деплой.
Миграции применяем отдельно, локально с боевым `DATABASE_URL`:

```bash
DATABASE_URL="postgresql://…" npm run db:deploy   # prisma migrate deploy
DATABASE_URL="postgresql://…" npm run db:seed     # кабинеты, услуги, права, демо-данные
```

### 4. Первый вход

После `db:seed` в базе есть владелец. Пароль задаётся отдельно — см. «Учётные
записи» ниже.

## Учётные записи

Свободная регистрация закрыта по умолчанию: публичная форма, выдающая права
администратора любому желающему, — дыра, а не удобство.

Работают два сценария:

1. **Первый запуск.** Пока в клинике нет ни одной учётки, `/register` открыт и
   создаёт **владельца**. Это способ войти в свежую установку.
2. **Дальше** сотрудников заводит владелец: «Настройки → Сотрудники» — имя,
   логин, пароль, роль. Для роли «Врач» там же выбирается специалист
   (существующий — чтобы не задвоить его в расписании), специальность и кабинет.

Персональные права каждого сотрудника — на его карточке
(«Настройки → Сотрудники → карточка»): каждое право переключается между
«как у роли», «разрешить» и «запретить».

Временно открыть регистрацию: `ALLOW_SELF_REGISTRATION=true`.

## Боевой контур на VDS/VPS

Всё поднимается одной командой из `docker-compose.yml`: приложение, PostgreSQL,
обратный прокси с TLS и ежедневные резервные копии. База наружу не публикуется —
она доступна только приложению внутри сети compose.

### Что нужно от сервера

Минимум 2 ядра и 4 ГБ памяти, Docker и Docker Compose, домен, направленный
A-записью на адрес сервера. Порты 80 и 443 открыты — Caddy сам получит
сертификат Let's Encrypt.

### Порядок

**1. Сгенерируйте секреты.** Каждый — своей командой, не переиспользуя:

```bash
openssl rand -base64 32          # SESSION_SECRET
openssl rand -base64 32          # CREDENTIAL_MASTER_KEY — ровно 32 байта, иначе
                                 # приложение откажется шифровать ключи интеграций
openssl rand -base64 32          # POSTGRES_PASSWORD
npx web-push generate-vapid-keys # VAPID_PUBLIC и VAPID_PRIVATE
```

`VAPID_PUBLIC` — 87 символов, `VAPID_PRIVATE` — 43, это **разные** строки.
`NEXT_PUBLIC_VAPID_PUBLIC` должен точно совпадать с `VAPID_PUBLIC`. Ошибка в
этих трёх полях выключает push целиком и молча — так уже было.

**2. Заполните настройки:**

```bash
cp deploy/env.example .env
```

Именно `.env`: docker compose подставляет `${...}` в `docker-compose.yml`
только из файла с этим именем. Настройки в файле с другим именем попадут
внутрь контейнера, но домен и пароль базы в самом compose останутся пустыми.

**3. Запустите:**

```bash
docker compose up -d --build
```

Порядок соблюдается сам: сначала база, затем разовый контейнер `migrate`
накатывает миграции, и только после его успешного завершения стартует
приложение. Схема никогда не отстаёт от кода.

**4. Проверьте:**

```bash
curl https://ВАШ_ДОМЕН/api/ping     # процесс жив
curl https://ВАШ_ДОМЕН/api/health   # переменные, ключи push, связь с базой
```

`/api/health` показывает размеры ключей VAPID и предупреждает, если что-то
задано неверно. Это первое, что стоит открыть при любой странности.

### Резервные копии

Контейнер `backup` делает сжатый дамп при старте и дальше раз в сутки, хранит
14 дней. Копия пишется во временный файл и переименовывается только после
успеха — оборванный дамп не выглядит как готовый.

**Копии лежат на том же сервере, и этого недостаточно.** Отказ диска или
удаление сервера унесёт их вместе с базой. Настройте выгрузку наружу, например
ежедневным `rsync` на другую машину:

```bash
docker compose cp backup:/backups ./backups-local
```

**Проверьте восстановление до запуска, а не после аварии.** Копия, из которой
ни разу не восстанавливались, копией не считается:

```bash
# на тестовой машине
gunzip -c clinic-ГГГГММДД-ЧЧММСС.sql.gz | docker compose exec -T db psql -U clinic -d clinic_restore_test
```

Убедитесь, что пациенты, визиты и справочник ассистента на месте.

### Подключение YCLIENTS

Порядок важен — он же снижает цену ошибки:

1. Заведите ключи в «Настройки → Интеграции»: партнёрский токен,
   пользовательский токен, идентификатор филиала. Они шифруются
   `CREDENTIAL_MASTER_KEY` и в репозиторий не попадают.
2. Поставьте `YCLIENTS_ENABLED=true` и перезапустите: `docker compose up -d`.
   До этого момента ни одного обращения к их API не происходит.
3. **Начните с короткого периода.** Поставьте `YCLIENTS_HISTORY_YEARS=1`,
   нажмите «Выгрузить данные» и посмотрите на время и на сверку. Полная
   история за два года — только после того, как короткая прошла чисто.
4. Нажмите «Сверить с YCLIENTS» и убедитесь, что расхождений нет. Отчёт
   показывает, сколько сущностей у них и сколько у нас, и какие именно
   идентификаторы не доехали.
5. Вебхуки: адрес `https://ВАШ_ДОМЕН/api/webhooks/yclients`, секрет —
   `YCLIENTS_WEBHOOK_SECRET`.

### Подключение WhatsApp (Green API)

По §5 с Meta Cloud API напрямую не работаем: провайдер держит сессию и даёт
один вебхук. Всё, что знает о Green API, лежит в `lib/integrations/whatsapp` —
смена провайдера меняет только эту папку.

1. Заведите инстанс в личном кабинете Green API, привяжите номер клиники
   (сканирование QR) и дождитесь состояния `authorized`.
2. Впишите `idInstance` и `apiTokenInstance` в «Настройки → Интеграции».
   Они шифруются `CREDENTIAL_MASTER_KEY` и в репозиторий не попадают.
3. Придумайте секрет вебхука и задайте его **в двух местах**: переменной
   `GREEN_API_WEBHOOK_SECRET` и в кабинете Green API — «Настройки инстанса →
   Уведомления → Authorization token». Без него вебхук закрыт: открытый адрес
   позволил бы кому угодно писать в инбокс от имени пациента.
4. Адрес вебхука: `https://ВАШ_ДОМЕН/api/webhooks/whatsapp`. В кабинете
   включите уведомления о входящих сообщениях и статусах.
5. Поставьте `WHATSAPP_ENABLED=true` и перезапустите. До этого ни одного
   обращения к провайдеру не происходит.
6. Проверьте `/api/health`: там видно, включён ли канал и задан ли секрет.

**Что учтено и почему это важно.** Green API шлёт в один адрес разнородные
события: входящие сообщения, статусы доставки, эхо собственных отправленных
сообщений, смену состояния инстанса и звонки. Принять их за одно — самая
частая ошибка при подключении: статус «доставлено» превращается в сообщение
пациента, а свой же ответ прилетает обратно и запускает второй круг. Разбор
различает все эти типы и покрыт восемнадцатью тестами.

Также обрабатываются: групповые чаты и рассылки (не отвечаем — ответ ушёл бы
всем участникам), нетекстовые сообщения (фото и голосовые получают понятную
подпись вместо пустой строки), повторная доставка (по идентификатору
сообщения), неавторизованный инстанс и номер без WhatsApp (администратор
видит причину словами, а не «не отправлено»).

### Обновление

```bash
git pull && docker compose up -d --build
```

Миграции накатятся сами. Старый контейнер работает, пока новый не собран.

### Если что-то пошло не так

```bash
docker compose logs -f app        # что говорит приложение
docker compose logs migrate       # прошли ли миграции
docker compose ps                 # кто жив
docker compose restart app        # перезапуск без потери данных
```

Проверка живости `/api/ping` намеренно не обращается к базе: недоступность
базы не должна перезапускать приложение по кругу.

## Проверено перед публикацией

- сборка проходит при полностью отсутствующем `.env` — ни базы, ни секретов;
- продакшен-режим: 20 маршрутов открываются без ошибок, на 1400px и на 390px;
- вход по логину и паролю, отказ при неверном пароле, редирект на `/login` без сессии;
- регистрация закрыта по умолчанию и работает при `ALLOW_SELF_REGISTRATION=true`;
- страницы приложения не кэшируются service worker'ом — карточки пациентов не
  оседают в памяти устройства;
- 296 тестов, типы и линтер чисты;
- автономная сборка Next (`output: standalone`) собирается и весит 49 МБ;
- `docker-compose.yml` разбирается без ошибок.

### Что НЕ проверено и требует внимания при запуске

- **Образ Docker не собирался**: в среде разработки не было запущено демона.
  Первая сборка на сервере может потребовать правок — смотрите вывод
  `docker compose up --build`.
- **Форматы ответов YCLIENTS** написаны по документации, без живых ключей.
  Первое соединение почти наверняка потребует правок в маппинге — поэтому
  начинать нужно с одного года истории, а не с полной.
- **Восстановление из резервной копии** ни разу не выполнялось. Это первое,
  что стоит проверить на боевом сервере до того, как в базе появятся реальные
  пациенты.
