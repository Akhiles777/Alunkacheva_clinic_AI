# Instagram через прокси на Vercel

## Зачем прокси

Instagram напрямую с российского сервера не работает, и сломано обе стороны:

- **Входящие.** Meta не доходит до `alunkachevaclinic.ru`: в логах nginx нет ни
  одного запроса от Meta, хотя извне эндпоинт на `curl` отвечает 200.
- **Исходящие.** С сервера в РФ не открывается `graph.instagram.com`.

Прокси `ig-proxy` стоит на Vercel посередине и работает **только как транзит**:
у него нет ни базы, ни файлов, а тела запросов он не пишет в журнал. Postgres,
планировщик и данные пациентов остаются на сервере в РФ (152-ФЗ, CLAUDE.md §7).
Переносить основной проект на Vercel нельзя.

```
Meta ──POST/GET──▶ ig-proxy /api/webhook ──▶ alunkachevaclinic.ru /api/webhooks/instagram
                     (сразу 200 для Meta)       проверяет X-Proxy-Secret и подпись Meta

clinic ──X-Proxy-Secret──▶ ig-proxy /api/graph/… ──▶ graph.instagram.com/…
```

## Кто что проверяет

| Проверка | Где | Чем |
|---|---|---|
| Запрос пришёл от нашего прокси | сервер клиники | `X-Proxy-Secret` = `INSTAGRAM_PROXY_SECRET` |
| Событие написала Meta | сервер клиники | подпись `X-Hub-Signature-256` секретом приложения |
| Слово проверки при подключении вебхука | сервер клиники | «Интеграции» → «Слово проверки вебхука» |
| Запрос к Meta — от нас, а не от посторонних | прокси | `X-Proxy-Secret` = `PROXY_SECRET`, без него 403 |

У прокси нет ни секрета приложения Meta, ни слова проверки, ни токена
страницы. Токен идёт от сервера клиники заголовком `Authorization` и
пересылается как есть. В адрес запроса его не кладём: адреса пишет журнал
Vercel.

## 1. Развернуть прокси на Vercel

Прокси — отдельный репозиторий `ig-proxy`: Next.js с двумя маршрутами,
`/api/webhook` и `/api/graph/[...path]`, оба на edge runtime.

1. Залейте репозиторий `ig-proxy` на GitHub и импортируйте его на Vercel
   (Add New → Project). Framework определится сам: Next.js.
2. Придумайте общий секрет:
   ```
   openssl rand -hex 32
   ```
3. Vercel → Project → Settings → Environment Variables (окружение Production):

   | Переменная | Значение |
   |---|---|
   | `ORIGIN_URL` | `https://alunkachevaclinic.ru` — без завершающего слэша |
   | `PROXY_SECRET` | строка из шага 2 |

4. Deploy. Если переменные меняли после развёртывания, нужен Redeploy: Vercel
   читает их при сборке.
5. Запомните адрес проекта, например `https://ig-proxy.vercel.app`.

Замечания:
- План **Hobby** на Vercel разрешён только для некоммерческого использования.
  Для клиники нужен **Pro**.
- Deployment Protection (Vercel Authentication) должен быть **выключен** для
  Production: иначе Meta получит страницу входа Vercel вместо вебхука.

## 2. Настроить сервер клиники

В `/var/www/clinic/.env`:

```
INSTAGRAM_ENABLED="true"
INSTAGRAM_GRAPH_BASE="https://ig-proxy.vercel.app/api/graph"
INSTAGRAM_PROXY_SECRET="<та же строка, что PROXY_SECRET на Vercel>"
```

`INSTAGRAM_GRAPH_BASE` указывается без версии API и без слэша на конце: версию
(`v21.0`) код добавляет сам. Адреса Meta в коде нет. Если переменная не
задана, отправка отвечает «не задан INSTAGRAM_GRAPH_BASE», а не «Instagram не
отвечает».

**Уберите из `.env`** `INSTAGRAM_APP_SECRET`, `INSTAGRAM_VERIFY_TOKEN` и
`INSTAGRAM_GRAPH_URL`, если они там есть. Код их больше не читает.

Выкатка:

```
cd /var/www/clinic && git pull --ff-only && bash deploy/pm2-deploy.sh
```

Миграций здесь нет, pm2 перечитывает `.env` при выкатке.

## 3. Ключи Instagram — в «Настройки → Интеграции»

В блоке Instagram три поля. Они хранятся в таблице `Credential`,
зашифрованные `CREDENTIAL_MASTER_KEY`, как ключи YCLIENTS и Green API:

| Поле | Откуда взять |
|---|---|
| Токен страницы | кабинет Meta → приложение → Instagram → токен доступа |
| Секрет приложения Meta | кабинет Meta → App settings → Basic → App Secret (раньше это был `INSTAGRAM_APP_SECRET`) |
| Слово проверки вебхука | любая строка, которую вы придумаете; раньше это был `INSTAGRAM_VERIFY_TOKEN` |

Если значения стояли в `.env`, скопируйте их сюда **до** того, как удалите их
оттуда. Без секрета приложения вебхук отвергает все события: 401 «invalid
signature».

## 4. Подключить вебхук в кабинете Meta

Meta → приложение → Instagram → Webhooks:

- **Callback URL:** `https://ig-proxy.vercel.app/api/webhook`. Это адрес
  ПРОКСИ, не сервера клиники. На экране «Интеграции» он показан готовым.
- **Verify token:** то же слово, что в поле «Слово проверки вебхука».
- Подписка на поле `messages`.

При нажатии Verify цепочка выглядит так: Meta → прокси → сервер клиники. Сервер
сверяет слово и отдаёт `hub.challenge` строкой, прокси возвращает ответ Meta
как есть.

## 5. Проверить

На сервере:

```
cd /var/www/clinic && npx tsx scripts/instagram-check.ts
```

Скрипт ничего не меняет и никому не пишет. Он показывает, что задано, и
проверяет связь в обе стороны:

- `мы → прокси → Meta: работает`: запрос без токена дошёл до Meta, и Meta
  ответила, пусть и отказом в авторизации;
- `прокси → сервер клиники: работает`: прокси достучался до нашего вебхука с
  верным секретом.

Руками с любой машины:

```
# прокси жив, доходит до сервера клиники и секреты совпадают → pong
curl 'https://ig-proxy.vercel.app/api/webhook?hub.mode=ping'

# без секрета прокси к Meta не пускает → 403
curl -i https://ig-proxy.vercel.app/api/graph/v21.0/me
```

## Наблюдение: прокси — новая точка отказа

Упавший прокси выглядит точно так же, как «сегодня никто не писал». Поэтому
планировщик сервера клиники проверяет его **раз в пять минут** (и один раз через
30 секунд после старта), в обе стороны:

- каждая неудачная проверка пишется в журнал pm2: `[instagram-proxy] проверка
  не прошла: …`;
- после **двух неудач подряд** (10 минут без связи) администраторам,
  управляющим и владельцу приходит уведомление «Instagram: связь потеряна». Оно
  появляется в колокольчике и уходит push-ом. Одиночный сбой, например
  перезапуск приложения, людей не будит;
- когда связь вернулась, приходит одно уведомление «Instagram: связь
  восстановлена».

Состояние видно на экране «Настройки → Интеграции» в строке «Связь через
прокси» и в `/api/health` в поле `прокси_instagram` и в `warnings`. Пока
`INSTAGRAM_ENABLED` не `true`, проверка не идёт: к Meta не уходит ни одного
запроса.

Как читать причины:

| Сообщение | Что чинить |
|---|---|
| Прокси недоступен — нет связи с Vercel | Vercel или сеть сервера; открыть адрес прокси в браузере |
| Прокси отказал: секрет прокси не совпадает | `PROXY_SECRET` на Vercel ≠ `INSTAGRAM_PROXY_SECRET` |
| Сервер клиники не принял секрет прокси | то же самое, только в обратную сторону |
| Прокси работает, но не достучался до сервера клиники | `ORIGIN_URL`, nginx, сертификат, работает ли приложение |
| Прокси не настроен (ORIGIN_URL, PROXY_SECRET на Vercel) | переменные на Vercel и Redeploy |
| Прокси работает, но сам не дотянулся до Instagram | сбой на стороне Meta, ждать |

## Поведение при сбоях

- **POST от Meta.** Прокси отвечает Meta 200 сразу, а пересылку делает следом
  через `waitUntil`: Meta ждёт быстрый ответ, иначе повторяет доставку и может
  отключить подписку. Если сервер клиники не отвечает на соединение или
  отдаёт 502 (приложение перезапускается), прокси повторяет пересылку ещё
  два раза, через 1 и через 3 секунды. Таймаут не повторяется: сервер мог уже
  ответить пациенту. Повторы безопасны, потому что сервер отбрасывает
  повторные события по `mid` сообщения.
- **Что при этом теряется.** Если сервер клиники лежал все три попытки,
  событие потеряно: Meta уже получила 200 и повторять не станет. В журнале
  Vercel остаётся `[ig-proxy] событие НЕ доставлено серверу клиники`. Поэтому
  уведомление о восстановлении связи просит заглянуть в сам Instagram.
- **Прокси не настроен.** На POST он отвечает Meta 500, а не 200: пусть Meta
  повторит доставку, когда прокси настроят, вместо молча пропавшего
  сообщения.
- **Отправка из платформы при упавшем прокси.** Сообщение не уходит, у него
  появляется причина словами («Прокси Instagram недоступен — нет связи с
  Vercel»). Вслепую отправка не повторяется: запрос мог дойти до Meta.

- **Что прокси не пересылает вовсе.** Прокси открыт всему интернету и к
  каждой пересылке прикладывает наш секрет, поэтому пересылает только то, ради
  чего существует. POST без подписи Meta получает 401, тело больше 256 КБ —
  413, GET с любым `hub.mode`, кроме `subscribe` и `ping`, — 400. Сервер клиники
  такие запросы не видит.

## Что идёт через Vercel

Через прокси проходят тексты сообщений пациентов из Instagram и ответы на них.
Эти данные уже лежат у Meta, но прокси — ещё один зарубежный обработчик на их
пути. Он их не хранит, и в журнале Vercel остаются только коды ответов. Адреса
запросов Vercel пишет сам: в адресе верификации есть слово проверки
(`hub.verify_token`), и больше ничего секретного в адресах нет.

Кроме Graph API, вложения пациентов (фото, голосовые) лежат на CDN Meta
(`lookaside.fbsbx.com` и подобных), и `/api/media` скачивает их напрямую. Если
CDN с российского сервера тоже закрыт, сами сообщения будут приходить, а
вложения не откроются. Это отдельная задача, и прокси её не решает.
